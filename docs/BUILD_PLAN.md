# Dark factory: build plan (v3)

Status: v3.1, 2026-10-08 (owner decisions recorded in section 3). Evidence chain: wave-one research (`research/01-07`), wave-two verification and audits (`research/wave2/`), wave-three full-text paper reading and independent re-verification against the arXiv PDFs (`research/wave3/`, `research/wave3/audit/`). Decisions marked **OPEN** need the owner before the phase that depends on them. The plan is use-case agnostic: the FastAPI pin and the multi-harness messaging tool are worked examples and live in `examples/`, not in the core design.

Evidence policy: a figure appears here only with its scope (model, benchmark, denominator). `[U]` marks a guess or design choice; `[unreachable]` marks a source that could not be opened. Do not hard-code a `[U]` number. All paper models are 2024 to 2026; none is a Claude 5.x measurement, so every rate below is a prior, to be re-measured in Phase 1 to 3 on our own repos.

## 1. Agreed design

### Core abstraction: the goal
Every unit of work is a **goal**: objective, machine-checkable success criteria, constraints, allowed outcomes, external state, and an escalation rule. Goals can spawn sub-goals (a DAG). The four use cases are goal types:

| Type | Example | Notes |
|---|---|---|
| `update` | Upstream changed (library, CLI, API, model) | The harness-compat case is an example, not the spec |
| `solve` | Long-running hard problem | Needs a progress signal and stall detection |
| `compare` | Try N options, pick the best | Gates, then metrics, then judged criteria |
| `build` | Greenfield build from a conversational vision | Factory proposes definition of done; user owns acceptance; rejection spawns a new round |

### Allowed outcomes
`adapt`, `pin/hold`, `constrain`, `work around`, `escalate`. Pinning is a successful outcome, recorded in the **constraints registry** with reason, evidence, upstream link and a revisit trigger, and re-tested on a loop so pins cannot silently rot (doc 05).

Adapt attempts are expected to fail often. Best measured LLM repair: 27% (28/103) of builds fully repaired (compile and tests), o3-mini, best of 40 model-by-prompt cells, on a Java/Maven compile-failure subset of BUMP (Byam, arXiv 2505.07522; 18 to 27% across prompts). So adapt has a bounded budget and falls through automatically to pin/constrain. Adapt success is build-level only (no partial fixes). The four-state check (the repair alone, without the version bump, must not make the new tests pass) is adapted from DepBench's task-validation oracle (arXiv 2608.30300); DepBench applies it to benchmark tasks, not to agent output, so using it as an anti-gaming gate is our design `[U]`. DepBench context: best of 10 agent configs solved 104/203; Claude Code + Opus 4.8 79/203; only 10 Python tasks.

### Autonomy rule
Proceed when one option is clearly dominant. Auto-merge on green CI plus canary plus verifier pass (the owner's rule). **Design tension to confirm with the owner:** green CI alone is not a safe merge signal (agent PRs: each failed check cuts merge odds by about 15%, OR 0.85, but humans reviewed those merges; no study covers unattended auto-merge). So auto-merge additionally requires the verifier's `pass` with clean integrity, a diff within policy size limits, and no sensitive-path touches; otherwise escalate. Escalate for architectural/design changes, genuine forks, and real ambiguity. Autonomy is set per repo in `.factory/policy.yaml`. Escalation is asynchronous: park the question, continue unblocked goals. Supervisor auto-merge deliberately exceeds Copilot's human-merge baseline (A-08). A worker may always choose "escalate/give up"; ImpossibleBench's abort option cut GPT-5 cheating from 54% to 9% (o3 49% to 12%) on Conflicting-SWEbench with a strict prompt, with a much smaller effect for Claude Opus 4.1 (2025 models).

### Architecture

**Supervisor.** Plain code (not an LLM), one daemon on SQLite (WAL) plus launchd jobs on the Mac host (or systemd timers inside the Linux VM). Owns the state machine, leases, budgets, ledger and stall detectors. Agents propose; the supervisor disposes. Temporal/Redis deferred. The Agent SDK and Claude Code provide per-run caps, local session persistence/resume and an optional external session store, but no goal state machine, cross-process lease, cross-run ledger, idempotent side effects or escalation (W2-02, verified). SessionStore is used only for cross-host resume. Do not use `claude --bg` as a runner. Temporal/Restate replay fit for LLM calls is confirmed only secondhand; the real objection is the extra server and workflow-code discipline.

**Execution.** `claude -p --bare` or the Agent SDK, API-key auth (billing decision deferred, so keep the auth method behind a config setting), in a container inside a Docker Linux VM on the Apple Silicon Mac host, plus a git worktree per attempt. The VM's CPU and memory allocation is the real concurrency limit; every tool image the goals use must run on arm64 (unchecked).
- Re-issue turn and USD caps on every invocation. `--max-budget-usd` ignores spend restored by `--resume`, so the factory's own ledger is the authoritative budget. Pin full model IDs and the Claude Code version; capture a stream-json fixture.
- Fresh session per attempt by default; fresh vs resumed context is a per-model config. No controlled study compares them.
- Stop on SIGINT then SIGTERM; handle `RESUME_INTERRUPTED_TURN`.
- "Keep going until CI is green" is a supervisor loop. Stop hooks (and `/goal`) are capped at 8 consecutive continuations and are only a backstop.
- Safety rests on deny rules and exit-2 hooks, not PreToolUse command hooks (they fail open on timeout and non-2 exits). Run a startup self-test that proves each deny rule and hook fires. If the SDK is used, prefer SDK callback hooks for policy gates (fail closed).
- Sandbox: non-root, always `--bare` with explicit config, `dontAsk` mode with explicit allow and deny rules.
- Classify all three limit responses: spend-cap 429, workspace 429 with retry-after, self-set-limit 400. Record the actual rate-limit tier; cap concurrency from TPM.
- Prompt cache: 1-hour TTL only for attempts that wait over 5 minutes; measure hit rate first.
- Export OpenTelemetry (Prometheus port 9464 verified).
- `claude-code-action` is not on the core path (self-hosted runner support undocumented). Use ephemeral self-hosted runners.
- Haiku 5.5 costs more above 100K tokens; a safety fallback can silently swap a model, so flag verifier model-tier changes.

**Roles and models.** Planner, worker (fresh context, one task, cannot edit criteria, may escalate), verifier (separate context, sole writer of `satisfied`). Opus 5.5 plans and verifies, Sonnet 5.5 works, Haiku 5.5 for cheap subagents; Fable 5.1 only for the hardest greenfield planning. Re-check model IDs and prices on the public pricing page. Multi-agent is not the default for coding work.

Why an independent verifier: LLM self-verification is unreliable (a Valmeekam-style LLM verifier passed 38 of 45 invalid plans; self-critique 55% vs 88% for a sound verifier, planning tasks, not code), and 60 of 88 fixed-test-passing submissions were broken by independent verifiers (SWE Refactor Bench). No matched builder-self-check vs separate-verifier study exists. Anthropic's March 2026 harness post calls separating doer from judge "a strong lever" and Claude "a poor QA agent" out of the box.

**Verifier.** Independence means information isolation (A-04):
1. The builder cannot read or edit the scorer.
2. No git-history leak (`git log --all`, shared remote).
3. No network route to verifier artifacts, including third-party mirrors. A leak study across five open-weight agents (arXiv 2609.06780) finds network and upstream access dominate (25 to 66% of exploits) and local git is about 6 to 22% (a lower bound; LLM-judged categories); a prompt cuts totals to 1.5 to 10.7% but local git persists at 0.3 to 8.6%.
Implementation: separate repo, runner label, token and required-status check. Deterministic checks first (contract, replay, held-out tests, surface diff), LLM judges last. One `VerifyRequest/VerifyResult` interface for all four goal types, with `judge_model_id` in criteria evidence.
- Judges: pairwise, order-swapped. The "Coin Flip Judge" figures (86.6% one trial, about 90% at 3, 95% at 11, arXiv 2606.13685) measure agreement with the same judge's own 50-trial majority, on two OpenAI mini judges and 29 near-tied general pairs (3 coding). They are not accuracy and not code-specific, so trial counts are `[U]`. Position bias is not established (72% A-majority for GPT-4o-mini, p=0.024; 59%, not significant, for GPT-4.1-mini). Pairwise beats pointwise for code (pointwise ties about half the time, CodeJudgeBench).
- Self-preference is measured for Claude judges (Sonnet 4.5 ratio 1.78, Haiku 4.5 1.71 on LiveCodeBench; Sonnet about 1.6 on IFEval with reasoning on; arXiv 2604.06996). A 5-judge committee reduces but does not remove it. So blocking judge-only criteria need a non-Claude juror in a panel (decided: add one from the start, called through any non-Anthropic model path the owner has available, such as another vendor's API or CLI), and each juror is calibrated separately.
- Comment-stripped diff for judges is a cheap injection mitigation `[U]`: CodeJudgeBench v2 shows removing comments slightly lowers accuracy and does not test misleading comments.
- Calibration: few-shot plus hard thresholds plus a kappa gate (>= 0.61 on 50+ labelled examples, guess `[U]`) before any judge gates. Pin the judge model id; recalibrate on change. The outcomes grader is still Claude.
- Differential test against the prior version is a non-blocking divergence report `[U]`. Strengthened acceptance tests are required: the oracle can be wrong (UTBoost: 28.4% (170/599) of patches passing 23 flagged Lite instances and 15.7% (92/584) on 26 flagged Verified; PatchDiff: 7.8% of patches differ in behaviour, +6.4 points in v2; SWE-ABS rejects 19.78% (2,184 of 11,041); UTBoost and SWE-ABS share a first author).

**Anti-gaming.** Protected paths for criteria/tests, test-diff policy, mutation testing on changed lines only (gate on no regression, not an absolute threshold; no paper tests mutation on LLM-written code, changed-lines support is human code at Google, arXiv 2102.11378), quarantine-by-builder is an integrity violation recorded as `event(type='integrity_violation', payload=evidence)`. Sandbox egress denies fetching upstream fixes during `solve`/`update`. Scale: EvilGenie's 20.7% is "heuristic" solutions, which the paper separates from hacking (strict figures for Claude Code with Sonnet 4: 2.1% hardcoding, 0% test edits). The Reward Hacking Benchmark finds combined hardening (four toggles, 13 models) cut exploits from 6.5% to 0.8% (-5.7 points). So rely on property/held-out tests for correctness and on environment hardening for gaming.

**Sandbox security.**
- No long-lived forge/cloud/registry tokens in the sandbox. The model key is injected by a proxy or is short-lived. Default-deny egress except provider APIs, with request-level checks (an allow-listed host can carry an attacker's key).
- Upstream-tool environment: self-updaters disabled, an explicit permission mode, and per-run config/home dirs. Tools are invoked by absolute path with explicit arguments, never bare, and an unvetted version is never run just to read its version string. (A worked example with a concrete hazard is in `examples/harness-compat.md`.)
- Untrusted upstream text (release notes, changelogs, issues, diffs) is data. Split readers of untrusted text from privileged agents; the worker has no secrets or egress; writes are confined to safe outputs. Prompt-level defenses are not a control: detector-type defenses were bypassed at 78 to 93% under adaptive attack (SoK, Table III, citing Nasr et al.); run-tests tasks are the highest-risk class (CIPR, Codex+GPT-5.4: 45.5% vs 8.6% for bug fixes; Claude Code + Sonnet-4.6 about 10 to 13% vs 3 to 5%, same ordering); poisoned rules files reach 41 to 84% (AIShellJack, editor/model pairs). Enforce scope with the sandbox, not the prompt (consent-stripping: GLM-4.6 in Claude Code 0.0 to 17.1%; Sonnet-4.6 3.9 to 15.8%; the effect shrinks to 2.6 points under randomized scenarios).
- Equal, recorded sandbox resources for compare goals (resource limits alone swung scores by 6 points).

**Merge controls and kill switch.** One branch per attempt. The worker credential cannot approve or merge; the merge credential is held only by the supervisor. Rationale and confidence are recorded per decision. Do not rely on agent self-reported confidence alone (verbalized confidence on SWE-bench: AUROC 0.70 to 0.83, ECE up to 0.50 for Gemini 2.5 Flash; Claude Sonnet 4.6 AUROC 0.794, ECE 0.109). Guard rails from agent-PR studies (human-reviewed repos, so optimistic for an unattended factory):
- Escalate on size: Claude Code PRs have a median 495 changed lines vs 52 human; more commits per PR correlate with more verified follow-up fixes (10x commits, 6.1x odds).
- Track per agent and per task class: merge rates by class are docs 84%, CI 79%, build 74% across agents (the 80 to 90%+ figure is Codex-only); revert proxies (90-day, commit-message based on the PR's most-changed file, not a floor) are Codex 6.1%, Devin 14.5%, human baseline 11.5%. Merged agent PRs get verified follow-up fixes at 1.62x human odds (4.5% within 30 days). Budget for a revert rate in this range and measure it against a human control `[U]`.
- Fix-forward by the same agent (69.6% in the data) is capped at N attempts.
- Prefer ask-to-continue frameworks (OpenHands overeager rate 0.2 to 4.5% vs 5.4 to 27.7% for permissive ones).
A fleet kill switch (flag checked before every lease, plus forge-token revocation, outside the agent's reach) is good practice, not an evidenced pattern. Anthropic's auto-mode 17% false-negative rate (n=52, Wilson 95% CI about 9 to 30%) is direction only; Claude Code + Sonnet-4.6 is the worst cell in the consent-stripping study (27.7%). Per-goal and per-day USD caps plus a consecutive-failure stop. Post-merge: a revert path (supervisor-generated revert PR, pin re-application); a post-merge canary failure triggers revert. Verify that PRs opened with a runner's default token do trigger CI on Forgejo Actions (GitHub's default `GITHUB_TOKEN` does not; Forgejo behaviour unverified): use a dedicated bot token.

**Detection.** Self-hosted Renovate (needs Node 24) or the factory's own watchers for detection and PR mechanics only. Decisions live in the factory (docs 01, 05). Generated Renovate config must null `minimumReleaseAge` for `lockFileMaintenance` and other unsupported update types (test; unproven). Dependabot `ignore` can suppress security fixes, so run an independent advisory scan.

**Cooldown (policy, not evidence).** Default 3 days with a 7-day profile. Adoption data: of ecosystem-level cooldown configs that set a default, 64.3% (157 of 244) use 7 days; 135 adopters among 1,462 popular repos; the paper offers no effectiveness evidence (arXiv 2609.16605). Verified native options: uv, pip, npm, pnpm (use strict), Dependabot (3-day default, version updates only). Cargo native cooldown needs Rust >= 1.100 (beta now; stable about 2026-11-12); gate Cargo on crates.io `pubtime` until then. Go: prefer `index.golang.org` `Timestamp`, with the factory's first-seen store as fallback. The PyPI 14-day rule is not a cooldown. Security updates bypass cooldown but not the canary. Incident windows (Axios, s1ngularity, Ultralytics, xz) come from vendor snippets `[unreachable]`.

**Update-goal testing rules.**
- Reruns: 3 for deterministic classes (compile, import, missing symbol). For behavioural failures, rerun only the failing tests, paired and interleaved on the new and current versions, and blame the update only if **every** new run fails and **every** old run passes. Choose the run count from the false-positive budget, for a test that fails half the time: 2 runs per side for 10%, 3 for 2%, 4 for 0.5%, 5 for 0.1%. "Any failure" or majority rules have a worst case of 25% however many runs, so do not use them. Mixed results escalate. Record per-test flake history. (Gruber's ~170 is the median reruns to expose flakiness in an already-flaky non-order-dependent Python test; it is not a stability rule.)
- Bisect: confirm the boundary with paired reruns at `last_good`, `first_bad` and `first_bad+1`, then search.
- Constraint syntax: a cap while the bad range's upper end is unknown; switch to exclusions once a fixed version is confirmed; compile per ecosystem (Cargo has no `!=`, npm uses `<X || >X`, Go uses exclude/retract). Tag `[U]`.
- Canary diffs transitive dependencies too. Breakage priors (scope matters): Hejderup, mean per-project test detection 47% direct / 35% indirect on Java/Maven mutants; Venturini, npm 44% each for minor and patch (87.5% combined) of manifesting breaks; Go, 28.6% of 59,527 non-major upgrades break at API level, 33.3% of clients of breaking upgrades affected. BreakGuard's LLM-generated differential tests detect 30.3% (27/89, best of 9 configs); 95.1% is the crash share, not precision. Jayasuriya's 11.58% and 2.30% are `[unreachable]`.
- Evidence gap: no study covers CLI contract breaks, auto-merge outcomes, upper-bound caps or version bisection, and Python evidence is narrow (Montandon: 35% of scikit-learn clients and 21% of pandas clients exposed to default-argument changes). Build the replay set from real breaking updates in the target repos' own history.
- Observed bot merge rates (observational, confounded by adoption and auto-merge config): nf-core Renovate 98.46% vs Dependabot 72.13% (arXiv 2607.10839); non-security Dependabot PRs 70.13% (He et al.).

**Contract testing for CLI and API upstreams (generic).**
- Each upstream declares an observable contract: invocation flags, output or event schema, exit codes, config and auth paths, self-update behaviour. The contract is recorded as fixtures with fake shims for fast checks, plus a live smoke test within 24 hours of each new stable release (upstreams that release several times a week make a nightly cadence too slow).
- Liveness check: a run that exits 0 without the expected output fails.
- The contract covers invocation flags, not only output fields (one upstream removed a flag 93 days after deprecating it; one data point).
- A new enum value in an output schema is classified `ambiguous` or `breaking`.
- Use an API key, not a throwaway account, and track release channels (`stable`, `latest`) separately.
- Worked example, with concrete findings (event schemas, a version that executes fetched shell on a bare run, release cadence): `examples/harness-compat.md`.

**Escalation.** A `question` table (context, options, recommendation, default-after-timeout) with ntfy, a web answer page, and PR comments. Answers must parse strictly; unparseable answers are rejected, not mapped to a default; re-asks are capped (do not copy Attractor's first-choice fallback or no-default retry loop). ntfy `http` actions use a bearer header, max 3 actions, always a `view` link; test the web-client CORS path. Webhooks: Cloudflare Access Bypass on the webhook path plus HMAC check, 10 s limit, dedupe on delivery GUID, 3-day redelivery reconciler, receiver-side logging because Bypass is unlogged. User-owned chat tools can be added later as transport adapters. Asking helps: on hidden-information tasks, clarifying questions lifted the resolve rate from 54.8% to 69.4% (Sonnet 4.5, simulated oracle user).

**Stall detection (uncalibrated; calibrate in Phase 5).** OpenHands SDK defaults: 4 identical action+observation repeats; stuck on the 4th consecutive same-action error (nudge at 3); 3 A/B cycles (6 actions); monologue 3. These are tool defaults, not evidence. Add `attempt.action_fingerprint` and a duplicate-call metric (SWE-Marathon: identical calls up to 877 long, 32% duplicates in the worst scaffold, pass rate falling with run length, claude-code 41.9% to 3.2%). Stall detectors parse live stream-json (Phase 1). Flaky tests can cause false stalls; spend-cap stops are a separate stop reason.

**Planning guidance.** METR (arXiv 2503.14499 v4): the 80%-success horizon is 4 to 6 times shorter than the 50% one, doubling time 207 days; the paper stops at o3 and 2026 horizons are `[unreachable]`. Start the horizon budget at 30 to 60 minutes of human-equivalent work per leaf `[U]`, log actual durations, and calibrate. LLM-only self-grading never flips a criterion (self-correction without external feedback lowers accuracy, Huang et al., ICLR 2024, reasoning tasks, not coding agents). Fresh-context loops and Ralph-style loops have no controlled evaluation.

Failure-mode prior (MAST, v3, 1,642 traces, NeurIPS 2025 D&B; shares of all failure labels, sum to 100): step repetition 15.7%, unaware of termination 12.4%, premature termination 6.2%, no/incomplete verification 8.2%; the whole verification category is 23.5%. Earlier versions differ (v1, 151 traces: 11.5 / 6.54 / 8.64 / 9.16 / 31.41), so always cite the version.

## 2. Phases

Each phase ends with something runnable and a reboot/crash test where state is involved.

**Phase 0: Skeleton (no agent).** SQLite schema (doc 04, plus `attempt.action_fingerprint`), goal state machine, event log, one release poller for one dependency, generated `GOAL.md`/`PROGRESS.md` views. Exit: a goal moves through states from a poll event; `kill -9` mid-transition recovers with no duplicate effects.

**Phase 1: Sandbox runner.** Container launcher in the Docker Linux VM (set VM CPU/memory limits, confirm arm64 images for every tool image, measure bind-mount performance) plus worktree launcher for `claude -p` with stream-json, transcript and artifact capture, caps re-issued per run, authoritative ledger, lease and heartbeat, pinned Claude Code version plus captured fixture, startup self-test of deny rules, kill-switch flag, credential isolation, upstream-tool environment hardening, live stream-json parsing for detectors. Exit: an attempt runs, is killed (SIGINT then SIGTERM), and resumes from its last commit; a planted token in the worktree is unusable for outbound calls; a test records how a credits-only org bills `claude -p` versus SDK calls before any billing assumption is made.

**Phase 2: Update goals end to end (use case 1).** Constraints registry and `policy.yaml` schemas with validation; canary with a minimal consumed-symbol/import check plus lockfile and transitive diff (full surface-diff library stays in Phase 3); decision procedure; bounded adapt with automatic fall-through; bisect worker with boundary confirmation and cost caps; the blame-the-update rerun rule; PR creation (Forgejo API token), green/red read, auto-merge per policy including size and sensitive-path limits; post-merge revert path; re-test loop for pins. First targets: one ordinary library repo (FastAPI-style pin) and one CLI-contract repo. Metrics: adapt success rate, revert rate per agent and task class (with human control), flake rate per test, pin age and count. Exit: a deliberate bad upstream release produces a pin with evidence and a later fixed release removes it automatically; the factory's adapt rate is measured on a replay set of real breaking updates from the target repos' history.

**Phase 3: Verifier and conformance.** Separate verifier repo and runner. Surface extraction and diff library (CLI `--help`, event schemas, Python public API, lockfile). Conformance layout: per-upstream consumer contracts, recorded fixtures with fake shims, live smoke within 24 hours of each new stable version. Integrity checks. Judge calibration (kappa gate) for the Claude judge and the non-Claude juror separately. Exit: planted test-weakening is caught; planted breaking upstream contract change is classified `breaking`; planted new enum value is `ambiguous`/`breaking`; exit-0-without-output fails liveness; planted verifier read, `git log --all` and network fetch of verifier artifacts all fail; planted protected-test edit is caught.

**Phase 4: Escalation.** Question table and service, ntfy plus web answer page, timeout/default executor, strict answer parsing with capped re-asks, PR-review-as-answer ingestion. Read-only dashboard (goals, active pins, median pin age, open questions). Exit: a forced fork pauses one goal and others continue; a reply resumes it; an unparseable reply is rejected.

**Phase 5: Solve goals (use case 2).** Planner/worker/verifier loop with fresh-context iterations (per-model config), progress metric, stall/loop/drift detectors with the defaults above, response ladder (retry, replan, allowed outcome, escalate). Exit: a multi-hour goal survives a reboot, stalls are detected without self-reports, and LLM-only grading never flips a criterion. Phase 5b (deferred): best-of-N reusing Phase 6 machinery; tree search is costly (SWE-Search +23% relative at about 14x cost with GPT-4o, about 5x for other models) and compute-matched resampling closes much of the gap.

**Phase 6: Compare goals (use case 3).** N sandboxes (default 3, max 4; guess `[U]`) with equal recorded resources, scoring schema (gates, Pareto metrics, pairwise judges), dominance pre-check, comparison report as a choose-question when no option dominates. The selector is the bottleneck: R2E-Gym hybrid verifier 51.0% vs 43.7/42.8% alone; CodeMonkeys 66.2% is selection over 5 candidates, 4 from other teams (best member 62.8, random 60.9); SWE-Hero-32B with SWE-Lego-Verifier-8B Best@32 64.6 vs Pass@32 79.8 (best of 4 open verifiers chosen on the test set; mean Pass@1 60.1; gains +7.9/+5.2/+4.5). Frontier gains are small: pool mean 76.1 to selected 78.2 vs oracle 84.4 (N=3, mixed models, SWE-bench Verified); 83.1 to 86.5 vs 92.1 (N=5, Terminal-Bench V2) (arXiv 2607.05391; verifier is a closed API model scoring repeated pairwise passes). Stroebl: false-positive cost sets the optimal attempt count, measure it; do not cite a numeric cap. Hybrid verification (tests plus verifier) is the default for ranking gate survivors, behind a measurement. Copeland aggregation is a candidate (cheap at N <= 4). Exit: selector accuracy on a planted set including near-tie and polish-bias pairs; gate false-positive rate measured; a known-better option wins reliably across reruns. Evolutionary mode (numeric fitness only; crossover adds about 2.1 points in EvolRepair) is optional later.

**Phase 7: Build goals (use case 4).** Autonomous full builds remain hard even at the frontier: ProgramBench, 0/200 resolved for all 9 models, best model (Opus 4.7) passes at least 95% of tests on 3.0% of tasks; ProjDevBench, 27.38% of submissions accepted (20 problems); older: Web-Bench 25.1% Pass@1 (Claude 3.7 Sonnet), Commit0 6.12% of tests (Claude 3.5 Sonnet, stage 1), ProjectEval about 15% best case (GPT-4o). Metrics differ; do not average them. Steps: ambiguity-detection step before elicitation (ReqElicitGym, current frontier models: overall elicitation 0.07 to 0.32, Opus 4.5 0.08, style requirements below 0.01; Ambig-SWE detection accuracy 0.47 to 0.89), so add an explicit style/UX checklist; conversation-to-spec template; stop-asking rule (max about 5 questions `[U]`); ClarifyGPT-type clarification gains are real but version-dependent (70.96 to 80.80, GPT-4, MBPP-sanitized with humans; 68.02 to 75.75, four-benchmark average, simulated user); factory-proposed definition of done with a separate agent writing acceptance tests, validated (mutants, second generation, human sign-off on expected values); `goals.yaml` sub-goal DAG; walking-skeleton first milestone; milestone verification; traceability drift metric judged by the verifier (not the builder); acceptance page; rejection loop (max 3 rounds `[U]`) feeding a "DoD lessons" file. The lessons loop is an untested hypothesis: the only evidence (arXiv 2607.13091) is a single uncontrolled Microsoft deployment (human-curated rules from accepted review comments; 9 classes, 74 exposures, 0 recurrences; no baseline; model not named) and says nothing about autonomous rounds; watch for over-personalisation. No outcome study of Spec Kit/Kiro/BMAD or of spec drift exists (Panda 2606.30689 compares Spec Kit and OpenSpec on determinism and traceability). Record the first-pass acceptance rate. Exit: a small greenfield project is built, rejected once with feedback, and rebuilt in a follow-up round.

Optional later: microVM isolation tier, Managed Agents pilot behind an executor interface (beta, $0.08 per session-hour, excluded from ZDR/HIPAA), evolutionary mode, durable engine if hand-rolled resume gets painful.

## 3. Decisions

### Decided by the owner (2026-10-08)

- **Auto-merge gate:** green CI plus canary plus verifier pass (clean integrity) plus size and sensitive-path limits; anything else escalates. Set per repo in `policy.yaml`.
- **Forge and CI:** local Forgejo with Forgejo Actions runners. **First task before Phase 2:** verify ephemeral/one-job runner support (v15 is secondary-sourced only) and runner behaviour on the Mac host or inside the Linux VM; confirm whether Forgejo's default token triggers CI on PRs it opens.
- **Host:** Apple Silicon Mac, 32 GB or more, running Docker Linux VMs. Consequences: launchd instead of systemd on the host; containers instead of rootless Podman; no microVM tier (no `/dev/kvm` in the VM, treat as unavailable); arm64 images; concurrency of roughly 4 to 6 sandboxes after VM and host overhead `[U]`, so compare goals default to N=3 (max 4).
- **Phone and remote reachability:** Tailscale (or another VPN). The answer page and ntfy actions stay private; no public tunnel or Cloudflare Access is needed for the phone path. Webhook receivers only need to be reachable by the forge on the local network.
- **Chat transports:** not at first. Escalation uses ntfy, the web answer page and PR comments; user-owned chat tools (such as the owner's messaging tool) are added as adapters later, once the question table works.
- **Judges:** add a non-Claude juror from the start (see section 1). Needs a second provider path and a calibration set per judge.
- **Upstream issues and comments:** draft only, human approves before anything is posted.
- **Known-bad versions in downstream tools:** a downstream tool that depends on upstreams users install themselves ships a bundled known-bad list generated from the factory's constraints registry in each release.
