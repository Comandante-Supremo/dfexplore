## 2. Combinations across studies in earlier docs

- "19 to 27% full fix on Java" (BUILD_PLAN line 22): combines Fruntke-Krinke (19% zero-shot, 23% agentic, snippets only) with Byam (27% best cell). Both are Java/BUMP build-level repair, so a loose range is defensible, but the 27% is the maximum over 40 model/prompt cells on a 103-update filtered subset, and the 19% is the weaker method of a different paper on a different subset. Say "roughly 20-27% at best, Java only, best-of-many configs".
- "Semver labels are weak (53% of breakage in minors)" (05 line 69): the 53% comes from an unreviewed thesis abstract on Python; the other studies measure different things (npm 44% each in minor and patch; Maven "nearly half" of client-impacting breaks in non-major releases; Go 28.6% of non-major upgrades). These support the same qualitative point but must not be merged into one percentage.
- Hejderup 47%/35% (detection) with 58%/20% (coverage) are two different metrics from the same paper, not alternative estimates of one quantity.
- 28.6% x 33.3% (Go): the 33.3% is already conditional on an upgrade being breaking (clients of the 17,009 breaking upgrades), so multiplying gives a rough 9.5% of client-upgrades "may be affected", static and identifier-level, not "will break". Legitimate only as an order-of-magnitude.

## 3. Per-claim detail

### 3.1 Hejderup & Gousios (claim 1)
- PAPER: "Can We Trust Tests To Automate Dependency Updates? A Case Study of Java Projects", arXiv 2109.11921 (preprint dated 27 Sep 2021), JSS 183, 111097 (2022).
- EARLIER DOCS: tests detect 47% direct / 35% indirect; "also 58%/20%?".
- PAPER SAYS: Abstract: "tests only cover 58% of direct and 20% of transitive dependency calls ... tests can only detect 47% of direct and 35% of indirect artificial faults on average." Section 5.2: "The median detection rate score is 51% (mean: 47%) for direct dependencies and 36% (mean: 35%) for transitive dependencies." Section 5.1: median coverage 58% (mean 55%) direct; transitive median 21% (mean 26%) in the text, 20% in the abstract and RQ1 findings box. Their static change-impact tool Uppdatera: 74% direct / 64% transitive.
- WHAT "DETECT" MEANS: Detection Score = Detected mutants / All mutants (Section 4.3), an adaptation of mutation score. Artificial updates are PITest-based mutations of third-party functions that are dynamically observed to be called by the project, using simple logical-flaw operators (statement deletion excluded). Detected means the project's own test suite fails on the mutated dependency.
- POPULATION: 1,122,420 artificial updates for 311 Maven modules in 262 GitHub Java projects (subset of 521 well-tested projects used for coverage). Per-project scores averaged, so it is per-project, not per-fault pooled. Ecosystem: Java/Maven only.
- CAVEAT (authors' own): "the applied mutation operators do not substitute actual regression changes in library updates". Real breaking updates are not simple mutants, so the rates are a coverage-gap indicator, not a real-world miss rate.
- VERDICT: CONFIRMED-WITH-SCOPE-CAVEAT. The journal version reportedly states 21% (not 20%) for transitive coverage (per search snippet and SLR 2605.24397 which cites 58%/21%).

### 3.2 Jayasuriya et al., ISSTA 2023 (claim 2)
- PAPER: "Understanding Breaking Changes in the Wild", ISSTA 2023, DOI 10.1145/3597926.3598147. No arXiv version found (arXiv search returned nothing; ACM, Zenodo, issta.org all blocked).
- EARLIER DOCS: 11.58% of Maven updates break clients.
- WHAT I COULD VERIFY: Search snippet of the abstract: 18,415 Maven artifacts, 142,355 direct dependencies, 71.60% not up to date, "11.58% of the dependency updates contain breaking changes that impact the client", about half of client-impacting breaks in non-major releases. Secondary, body-level read of arXiv SLR 2605.24397 (Table 4/5): "11.58% of dependency updates cause client-impacting breaking changes (latest version); 4.35% for adjacent version", citing the extended EMSE 2025 paper (Jayasuriya, Ou, Hegde, Terragni, Dietrich, Blincoe, EMSE 30(2):42). Same SLR: internal-API users break at 20.6% vs 11.58% overall; transitive changes are 20.36% of client-impacting source breaks.
- DEFINITION OF BREAK: not verifiable from a primary. Per snippets and SLR it is syntactic (source/API-level, client-impacting) breaking, detected by comparing library API changes against client usage and compiling, not behavioural failures. Unit is per dependency update (artifact x dependency x version), Maven only.
- VERDICT: UNREACHABLE primary. If the factory updates one release at a time, the relevant secondary number is 4.35% (adjacent version), not 11.58% (latest). Needs a primary re-read.

### 3.3 Venturini et al. (claim 3)
- PAPER: "I depended on you and you broke me: An empirical study of manifesting breaking changes in client packages", arXiv 2301.04563 v1 (11 Jan 2023); published ACM TOSEM 32(4), 2023.
- EARLIER DOCS: npm, 44% of manifesting breaks from minor/patch.
- PAPER SAYS: Abstract: "from all of the manifesting breaking changes, 44% were introduced both in minor and patch releases". Introduction: "an equal proportion of manifesting breaking changes was introduced in minor and patch releases (approximately 44% in each release type)". Table 4: Major 3 (4.7%), Minor 28 (43.75%), Patch 28 (43.75%), Pre-release 5 (7.8%), total 64. The study analysed only minor/patch provider updates; the 3 major cases came via indirect providers.
- So minor+patch = 56/64 = 87.5%, not 44%. The abstract wording is ambiguous and the earlier docs inherited the ambiguity.
- DENOMINATORS: 384 randomly sampled npm client packages (95% confidence, +/-5%), 3,230 releases tested; 203 clients / 1,276 releases failed install/test scripts, manually triaged; 55 unique provider-introduced breaks, 64 manifestations across clients; 51 of 1,909 providers (2.6%) introduced one. Impacted: 11.7% of clients and 13.9% of their releases during non-major updates of dependencies. Detection is via the client's own install/test script (so test-manifesting breaks only).
- VERDICT: CONFIRMED-WITH-SCOPE-CAVEAT. npm only, small manual sample (n=64).

### 3.4 Go study (claim 4)
- PAPER: "A Large-Scale Empirical Study on Semantic Versioning in Golang Ecosystem" (GoSVI), Li, Wu, Fu, Zhou, arXiv 2309.02894 v2 (18 Sep 2023), ASE 2023.
- EARLIER DOCS: 28.6% of non-major upgrades break at API level; 3.1% and 33.3% of clients?
- PAPER SAYS: Abstract: "86.3% of library upgrades follow SemVer compliance and 28.6% of no-major upgrades introduce breaking changes ... 3.1% of breaking changes affect client programs, while 33.3% of client programs may be affected by breaking changes." Table III: non-major 59,527 upgrades, 17,009 breaking (28.6%); minor 37.9%, patch 25.1%, major 59.6%, development (v0/pre-release) 28.4% of 63,079; all 124,532 upgrades, 36,060 breaking (29.0%). Table IV: 363,428 breaking changes, 11,304 used by clients = 3.1% (the text says 11,034, internal inconsistency). RQ3: 151,589 downstream clients of the 17,009 breaking non-major upgrades, 50,485 affected = 33.3%.
- DENOMINATORS: 28.6% is per library-version upgrade pair (GitHub-hosted Go modules, 2018-09 to 2023-04, 124K TPLs, 532K clients). 3.1% is per individual breaking change (API-level change instance), counting only whether client code references the changed identifier. 33.3% is per client program, conditional on its dependency upgrade being breaking, and is "may be affected" (static identifier resolution, not compile or test run).
- Also: compliance rose from 63.7% (2018/09) to 92.2% (2023/03); non-major breaking rate fell from 36.3% to 21.5% early and to 7.8% by 2023/03. The 28.6% is a pooled figure that overstates the recent rate.
- VERDICT: CONFIRMED-WITH-SCOPE-CAVEAT. Go only, static.

### 3.5 BUMP, Byam, DepBench, BDUpdater, J.P. Morgan (claim 5)
BUMP (arXiv 2401.09906 v1, SANER 2024): "571 breaking dependency updates collected from 153 Java projects" built with Maven. Section RQ2: "243 (43%) are due to compilation failures and 188 (33%) are due to test failures"; remaining are dependency-resolution and other failures. Java/Maven only. CONFIRMED.

Byam (arXiv 2505.07522 v3, 17 Feb 2026):
- Abstract: "OpenAI's o3-mini is the best, able to completely fix 27% of the builds ... Also, it fixes 78% of the individual compilation errors."
- Table 4: o3-mini P8 (CoT + erroneous line + API diff) = 28/103 builds (27%). "Completely repaired, with compilation and test execution succeeding." Column ranges: o3-mini 18%-27% over 8 prompts; DeepSeek V3 14-21%; Gemini 7-20%; GPT-4o-mini 13-17% (approx); Qwen 9-13%.
- Error level: 741/955 = 77.6% (Table; abstract says 78%, the introduction says 79%, a minor internal inconsistency). File level: 41%.
- Population: 103 of BUMP's 571 updates. They keep compile-failure cases only, dropping 78 Java-version incompatibilities, 8 Werror, and classpath/dependency-conflict cases that cannot be fixed by editing code. Median 3 initial errors, 70% affect one file. Build "success" requires compile plus tests passing.
- Best-of-40 selection on the same 103 cases, so the 27% is optimistic. Not an estimate for Python or for tests-only failures.
- "19-27%": 27% is Byam's best; Fruntke & Krinke (FSE 2025, DOI 10.1145/3729366, not on arXiv, UNREACHABLE) is reported in snippets as up to 23% agentic and up to 19% recursive zero-shot on BUMP. See section 2 for combination.

DepBench (Luo, He, Gao, Kang, Lin, Ma, Lin, Rajmohan, Tian; arXiv 2608.30300 v1, 31 Aug 2026; Monash/PKU/Microsoft):
- Abstract: 203 real-world dependency-upgrade tasks, five ecosystems (68 npm/yarn, 65 Maven/Java, 40 Go, 20 Cargo, 10 Python). "The best completed configuration solves only 104/203 tasks (51.2%)".
- Table II (pass counts): Codex + GPT-5.5 104; Copilot CLI + GPT-5.5 99; Claude Code + GPT-5.5 71; Claude Code + Claude Opus 4.8 79 (38.9%); Gemini 3.5 Flash 51-53. 104 is the maximum of the matrix, not a typical result. Python: best 6/10 (Table III), too few tasks for a Python estimate.
- Four-state oracle (abstract/Section III): from the same pre-upgrade state, (1) unmodified repo installs, builds and passes tests; (2) manifest+lockfile changes plus held-out tests must FAIL; (3) adding the developer repair makes them PASS; (4) developer repair plus held-out tests but WITHOUT the manifest/lockfile changes must still FAIL. This is applied to each candidate task by the benchmark builders (with human and LLM audit) to certify that the failure is tied to the upgrade. Agents are graded on a full-upgrade setting: start from the base repo, must preserve the version bump and repair source, then hidden tests are run.
- Implication: BUILD_PLAN line 22 describes the four-state check as something "a repair must pass". That is the factory's own design borrowed from the benchmark's curation logic; the paper does not use it as an acceptance gate on agent output and does not report that it prevents wrong repairs. Rephrase as "adapted from DepBench's task-validation oracle".
- VERDICT: CONFIRMED (numbers), scope-corrected (use).

BDUpdater: "Break to Adapt: Knowledge-Based Updates of Breaking Dependencies in JavaScript", Xia et al., FSE 2026 (PACMSE), DOI 10.1145/3808116. PDF (nesa.zju.edu.cn), researchr and doi.org blocked; no arXiv found. Abstract snippet only: 83.8% of top JS libraries maintain breaking change records in their repos, quality varies; BDUpdater is an agent-based framework. The 90.5% figure, "13 libraries / 84 clients", and the definition of "recovered" were not found in any accessible text. VERDICT: UNREACHABLE; do not hard-code 90.5% until read. The earlier doc's "given breaking-change records" qualifier cannot be checked.

J.P. Morgan (Tawosi, Alamir, Liu, Veloso; "LLM Agents for Automated Dependency Upgrades", arXiv 2510.03480 v2, 24 Nov 2025):
- Abstract: "achieves a precision of 71.4%". Section IV-C: "in the 3.2 to 3.3 upgrade, LADU's removals were more accurate (71.4% vs. OpenHands' 17.2%)".
- Metric: exact-match overlap of changed lines vs a manually upgraded "gold" repo, for one of three synthetic repositories (framework upgrades 3.1 to 3.2, 3.2 to 3.3, 3.3 to 3.4), a Java Spring Boot-based system. Compared with OpenHands + Claude 3.7 Sonnet; LADU uses GPT-4o. No builds or tests run as an outcome measure; no real repositories.
- Earlier doc ("71.4% precision on three synthetic repos") overstates: it is one upgrade, line-removal precision. VERDICT: WRONG as used; scope = one synthetic upgrade, line-removal precision.

### 3.6 BreakGuard (claim 6)
- PAPER: "BreakGuard: Towards Detecting Dependency Breaking Changes with LLM-Generated Tests", Raj, Baudry, Costa (Concordia, Montreal), arXiv 2608.20167 v1, 20 Aug 2026. Exists.
- PAPER SAYS: Abstract: "Using the best-performing configuration, BreakGuard detects 30.3% of breaking changes (27 of 89) at a mean cost of roughly $0.90 USD per detected breaking change ... LLM-generated tests to be more reliable for detecting crash-type breaking changes as opposed to behavioural BCs." Table V: GPT-4o class context 27/89 (30.3%); GPT-4o minimal 17 (19.1%), method 13 (14.6%); Qwen3-coder 18-20 (20.2-22.5%); GPT-OSS-120B 4-10 (4.5-11.2%).
- A test "detects a BC if it passes on the pre-breaking version and fails on the breaking version".
- POPULATION: filtered from BUMP (Table I): 571, to 188 test-failure instances, 179 after Docker timeout, 164 with JUnit4/5/TestNG, 104 after static analysis, 89 with call sites in production code. Java/Maven only; instances where the breakage is a failing test in BUMP's reference run.
- 95.1%: Table VI/VII: of 3,566 detecting tests, 3,390 (95.1%) end in a Surefire ERROR and only 176 (4.9%) in an assertion FAILURE; errors are NoClassDefFoundError 42.5%, NoSuchMethodError 29.0%, ClassNotFoundException 28.5%. Only 25 of the 176 assertion failures are value-based. This is the crash-type share of detecting tests, NOT precision. The paper reports no precision or false-alarm rate.
- VERDICT: 30.3% CONFIRMED (best of 9 configs, selected post hoc, n=89). 95.1% precision WRONG. Behavioural-break detection is weak (about 5% assertion failures).

### 3.9 Gruber et al. and the flaky arithmetic (claim 9)
- PAPER: "An Empirical Study of Flaky Tests in Python", Gruber, Lukasczyk, Kroiss, Fraser, arXiv 2101.09077, ICST 2021.
- PAPER SAYS: Abstract: "A 95 % confidence that a passing test case is not flaky on average would require 170 reruns." Section RQ3 answer (a): "In order to be 95% sure that a test case is not flaky due to non-order-dependent reasons, one would have to run it at least 170 times. For order-dependent flakiness, this number is lower, at 31 random-order executions." Finding (c): 110 reruns to find 80% of NOD flakiness, 472 for 95% confidence; OD: 49 and 209. Finding (b): ten reruns find at most 33% of NOD and 54% of OD flaky tests. Finding (d): "for the majority of NOD flaky tests, only 1 rerun is needed to achieve a statistical confidence of 95%" that a failure is flaky (3 for OD).
- Derivation: Ut(n) = 1 - (1-P(fail))^n - (1-P(pass))^n + ...; n_{t,0.95} = min n with Ut(n) > 0.95; the 170 is the median over tests in the dataset that were already observed flaky (952 NOD flaky tests), whose failure probabilities are typically low. Dataset: 22,352 PyPI projects, 876,186 tests, 7,571 flaky (0.86%), 400 reruns. Python/pytest only, infrastructure flakiness separated.
- So 170 answers "how many reruns to see any flip in an average flaky test"; it is not a requirement for regression-vs-flake attribution and is irrelevant to a 50/50 test (a flip is seen with 95% confidence in 6 reruns: 1 - 2(0.5^n) > 0.95 gives n = 6). The paper itself argues failure reruns are generally sufficient to identify a flaky failure. BUILD_PLAN already rejected "Gruber-170 justification"; this confirms that was right.
- ARITHMETIC (computed, independent runs, each run fails with probability p on both old and new):
  - Pattern "new fails all n runs and old passes all n runs", p=0.5: n=3 gives 0.5^6 = 1.5625% (the "1.6%"); n=5 gives 0.5^10 = 0.0977% (the "0.1%"). Correct for that strict pattern.
  - Pattern "new fails at least once, old passes all n": n=3 10.9%; n=5 3.0%.
  - Pattern "majority of n fail on new, majority pass on old": 25.0% for both n=3 and n=5 (more runs do not help at p=0.5).
  - For p=0.1: strict 0.07% (n=3); at-least-once-fail 19.8% (n=3) and 24.2% (n=5), which rises with n.
  - Conclusion: the 1.6%/0.1% figures are right for an "all-fail vs all-pass" decision rule; a decision rule that triggers on any new failure with a clean old run has a false-attribution rate roughly 7x to 30x higher for a 50/50 test.
